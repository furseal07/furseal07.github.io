    KEY LOGIC 직접 구현한 예약 · 결제 · 환불

    돈과 좌석이 걸린 흐름은 어느 단계에서 실패해도 어긋나지 않게 만들었습니다.

    01
    좌석 중복 예약은 DB가 막습니다

    애플리케이션 락 대신, 선점·확정 상태일 때만 걸리는 부분 유니크 인덱스를 두었습니다. 두 사람이 같은 좌석을 동시에 잡으면 한쪽은 제약 위반으로 예약 전체가 롤백되고 좌석 선택 화면으로 돌아갑니다.

    -- 선점(HOLDING)·확정(CONFIRMED) 티켓만 유니크 검사 대상
CREATE UNIQUE INDEX uq_ticket_active_seat ON TICKET (
  CASE WHEN hold_status IN ('HOLDING','CONFIRMED')
       THEN flight_id END,
  CASE WHEN hold_status IN ('HOLDING','CONFIRMED')
       THEN seat_id END
);
    02
    결제 금액은 서버가 다시 확인합니다

    브라우저가 보낸 값을 믿지 않고 PortOne 서버에서 결제 건을 다시 조회해 예약 원장 금액과 비교합니다. 금액이 다르거나 그사이 좌석 선점(10분)이 만료됐으면 자동으로 환불합니다.

    // 브라우저 값이 아닌 PortOne 서버 조회 금액으로 검증
SHIamportPayment p = iamportClient.getPayment(merchantUid);
try {
  shBookingService.confirmPayment(bookingId, ...,
      p.getAmount(), "PORTONE", null);
} catch (SHSeatTakenException e) {
  iamportClient.cancelPayment(merchantUid,
      "좌석 선점 만료 - 자동 환불");
}
    03
    결제가 실패해도 좌석은 반납됩니다

    실패 처리를 별도 트랜잭션으로 분리해 바깥 로직이 롤백돼도 좌석 반납은 커밋되게 했습니다. 만료된 선점은 1분마다 스케줄러가 정리하고, 확정 쿼리도 만료 시각을 함께 확인해 정리가 늦어도 잘못 팔리지 않습니다.

    @Transactional(propagation = Propagation.REQUIRES_NEW)
public void failPayment(Long bookingId, Long memberId) { ... }

@Scheduled(fixedDelay = 60_000)
public void releaseExpiredSeats() { ... }
    04
    환불은 두 번 일어나지 않습니다

    출발일까지 남은 일수별 수수료율로 티켓마다 환불액을 계산하고, 결제사 취소 → DB 반영 순서로 처리합니다. 이미 처리된 요청은 같은 결과를 돌려주고, 결제사에 부분 취소 이력이 있거나 그사이 티켓 상태가 바뀌면 중단합니다.

    // 결제사에 이미 부분 취소 이력 → 중복 환불 방지
if ("PARTIAL_CANCELLED".equals(remoteStatus))
  throw new SHRefundReconciliationException(...);

// 조회한 티켓 수 ≠ 실제 UPDATE 수 → 동시 변경, 전체 롤백
if (cancelledTickets != tickets.size())
  throw new IllegalStateException("티켓 상태가 변경되어 ...");

    KEY LOGIC 직접 구현한 채팅 · 클럽 · 관리자

    여러 사람이 같은 데이터를 건드리는 기능은 한 번의 처리로 끝까지 맞아떨어지게 만들었습니다.

    01
    채팅은 새 메시지만 가져옵니다

    3초마다 폴링하되 화면에 있는 마지막 메시지 번호를 함께 보내, 그 이후 메시지만 최대 30건 조회합니다. 같은 요청에서 상대 메시지 읽음 처리와 미읽음 수 갱신까지 끝내 응답 한 번으로 채팅 상태가 맞춰집니다.

    -- 마지막으로 받은 메시지 이후만 조회
SELECT * FROM (
  SELECT zc.chat_num, zc.message, ...
    FROM zboard_chat zc
   WHERE zc.chatroom_num = ?
     AND zc.chat_num > ?      -- lastChatNum
   ORDER BY zc.chat_num ASC
) WHERE ROWNUM <= ?          -- 30건
    02
    가입 승인은 한 트랜잭션에서 끝냅니다

    클럽 행을 잠근 뒤 신청 상태, 회원 상태, 다른 클럽 소속, 정원을 다시 확인하고 승인합니다. 1인 1팀 규칙에 맞춰 같은 회원의 다른 대기 신청은 자동 취소하고, 하나라도 실패하면 전체를 되돌립니다.

    conn.setAutoCommit(false);
// SELECT ... FROM clubs WHERE club_num = ? FOR UPDATE
if (isClubFullForUpdate(conn, clubNum))
  throw new IllegalStateException("CLUB_FULL");
// UPDATE ... SET status = 2 WHERE request_id = ? AND status = 1
// UPDATE ... SET status = 4  -- 같은 회원의 다른 대기 신청 취소
conn.commit();
    03
    팀장 양도는 한 번에 바뀝니다

    클럽 대표자 변경, 기존 팀장 강등, 새 팀장 승격을 하나의 트랜잭션으로 묶어 팀장이 둘이거나 없는 순간이 생기지 않게 했습니다. 알림은 커밋 뒤 따로 보내 알림 실패가 양도를 되돌리지 않습니다.

    // 1) clubs.user_num = newLeader
// 2) 기존 팀장 role = 1 (MEMBER)
// 3) 새 팀장   role = 2 (LEADER)
conn.commit();

try { sendTransferNotifications(cur, next); }
catch (Exception ignored) { } // 양도는 이미 완료
    04
    관리자 조치에는 안전장치를 둡니다

    회원 제재와 구장 상태 변경 전에 대상 행을 잠그고 현재 상태를 다시 읽습니다. 관리자 계정은 제재할 수 없고, 모집 중이거나 확정된 매치가 남은 구장은 폐쇄되지 않습니다.

    // SELECT role, status FROM users WHERE user_num = ? FOR UPDATE
if (targetRole == 9)
  throw new IllegalStateException("ADMIN_PROTECTED");

// 진행·예정 매치(status 1, 2)가 남은 구장은 폐쇄 불가
if (newStatus == 3 && countActiveMatches(conn, stadiumNum) > 0)
  throw new IllegalStateException("ACTIVE_MATCH_EXISTS");

    TROUBLE SHOOTING 문제 해결 기록

    반복되는 비용은 기준을 바꿔서 줄였습니다.

    TS 01
    채팅 전체 재조회를 증분 조회로 변경

    매번 모든 메시지를 다시 읽던 구조를 마지막 메시지 기준 조회로 바꿨습니다.

    SITUATION
    • WebSocket 없이 AJAX 폴링 방식으로 1:1 채팅 구현
    • 채팅방 입장·갱신 때마다 방의 전체 메시지를 조회
    TASK
    • 메시지가 쌓일수록 같은 데이터를 반복해서 조회·전송
    • 읽음 상태와 미읽음 수가 화면과 어긋날 수 있음
    ACTION
    • 마지막 메시지 번호(lastChatNum) 이후만 조회하도록 쿼리 변경
    • 새 메시지 조회 · 상대 메시지 읽음 처리 · 미읽음 수 갱신을 한 요청에서 처리
    • 응답 전 다음 요청이 겹치지 않도록 폴링 중복 방지
    RESULT
    • 폴링 응답에 새 메시지만 담겨 불필요한 조회 감소
    • 읽음 표시와 사이드바 미읽음 배지가 같은 기준으로 갱신
    TS 02
    화면별 스타일 차이를 디자인 시스템으로 통일

    네 명이 각자 만들던 화면을 공통 CSS 계층과 템플릿으로 묶었습니다.

    SITUATION
    • 4인이 역할별(사용자 · 클럽장 · 심판 · 관리자) 화면을 나눠 개발
    TASK
    • 버튼 · 카드 · 여백 스타일이 화면마다 달라 통합 때마다 반복 수정
    • 새 페이지를 만들 때 따를 기준이 없음
    ACTION
    • base(디자인 토큰) · layout(네비·헤더·푸터) · components(버튼·폼·카드·테이블) 3계층 CSS로 정리
    • header · footer를 공통 include로 통일
    • 새 페이지용 JSP 템플릿과 디자인 시스템 가이드 문서 작성
    RESULT

    KEY LOGIC 직접 구현한 시스템 관리자 기능

    관리자 기능은 데이터를 바꾸기 전에 허용된 변경인지부터 확인했습니다.

    01
    입력한 조건만 붙이는 회원 검색

    ID · 이름 · 이메일 · 권한 · 상태 · 가입일 · 마지막 접속일 9가지 조건 중 입력한 것만 WHERE 절에 붙입니다. 값은 모두 ? 자리에 바인딩해 SQL 문자열에 직접 섞지 않았습니다.

    StringBuilder sql = new StringBuilder(
  "SELECT ... FROM userInfo WHERE 1=1 ");
List<Object> params = new ArrayList<>();

if (!isEmpty(name)) {
  sql.append(" AND user_name LIKE ? ");
  params.add("%" + name + "%");
}
if (!isEmpty(regStart)) {
  sql.append(" AND TRUNC(user_created_at) >= TO_DATE(?, 'YYYY-MM-DD') ");
  params.add(regStart);
}
for (int i = 0; i < params.size(); i++)
  pstmt.setObject(i + 1, params.get(i));
    02
    권한 변경과 변경 이력은 함께 저장

    권한을 바꾸기 직전에 대상의 현재 권한과 계정 상태를 다시 읽고, 권한 UPDATE와 변경 이력 INSERT를 한 트랜잭션으로 묶었습니다. 둘 중 하나라도 실패하면 모두 되돌려 이력 없는 권한 변경이 생기지 않습니다.

    conn.setAutoCommit(false);
// SELECT user_role_cd, user_acct_status_cd ...
if (!"ACTIVE".equalsIgnoreCase(status)) {
  conn.rollback(); return 0;
}
// UPDATE userInfo SET user_role_cd = ?
// INSERT INTO role_change_hist (...)
//   VALUES (seq_role_change_hist.NEXTVAL, ?, ?, ?, ?, SYSDATE, ?)
if (inserted != 1) { conn.rollback(); return 0; }
conn.commit();
    03
    권한 신청은 대기 중인 건만 승인

    신청 상태를 바꾸는 UPDATE에 PENDING 조건을 걸어, 이미 처리된 신청은 0건으로 끝나고 다시 승인되지 않습니다. 승인과 신청자 권한 변경은 같은 트랜잭션에서 처리합니다.

    UPDATE role_application
   SET role_app_status = 'APPROVED',
       role_approved_at = SYSDATE,
       role_approved_by = ?
 WHERE role_app_id = ?
   AND role_app_status = 'PENDING'

-- 0건이면 rollback → "이미 처리되었거나 오류"
-- 1건이면 UPDATE userinfo SET user_role_cd = ? → commit
    04
    정지 기간 검증과 만료 자동 복구

    정지는 시작일 ≤ 오늘 ≤ 종료일일 때만, 연장은 기존 종료일 이후로만 허용합니다. 회원 관리 메뉴에 들어올 때마다 종료일이 지난 정지 계정을 ACTIVE로 되돌려, 관리자가 일일이 해제하지 않아도 됩니다.

    UPDATE userInfo
   SET user_acct_status_cd = 'ACTIVE',
       user_penalty_end_dt = NULL
 WHERE user_acct_status_cd = 'SUSPENDED'
   AND REGEXP_LIKE(user_penalty_end_dt,
                   '^\d{4}-\d{2}-\d{2}$')
   AND TO_DATE(user_penalty_end_dt, 'YYYY-MM-DD')
       <= TRUNC(SYSDATE)

    TS 01

    행을 지우는 대신 계정 상태를 DELETED로 바꿔 이력을 지켰습니다.

    SITUATION
    • 관리자 메뉴에 회원 계정 삭제 기능 필요

    TASK
    • 회원 행을 직접 지우면 기존 과제 · 권한 신청 데이터와의 관계가 훼손될 수 있음
    • 관리자 계정까지 삭제될 위험
    ACTION
    • 계정 상태를 DELETED로 바꾸는 논리 삭제로 구현
    • 삭제 전 존재 여부 · 이미 삭제 · 관리자 계정 여부를 먼저 확인 (NOT_FOUND · ALREADY_DELETED · ADMIN_BLOCK)
    • 목록 조회에서 DELETED 제외, DELETED 계정은 상태 · 권한 변경 차단
    RESULT
    • 관련 이력을 유지하면서 비활성 회원의 시스템 접근 제한
    • 관리자 계정 삭제 원천 차단

    SITUATION

    • 기간이 끝난 공고 재오픈, 과거 날짜 정지처럼 업무상 맞지 않는 변경 가능

    • 마감 → 공고중은 마감일이 남은 경우만, 정지는 시작일 ≤ 오늘 ≤ 종료일, 연장은 기존 종료일 이후만 허용
    • ACTIVE 계정만 권한 변경 허용
    RESULT
    • 잘못된 값이 DB에 닿기 전에 차단
    • 서비스 클래스마다 반복되던 입력 검증 코드를 한 곳으로 정리
